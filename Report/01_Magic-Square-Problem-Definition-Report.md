## 1. 요약

4×4 격자에 값을 배치할 때 **여러 규칙(합·중복·범위)이 동시에 성립하는지**를 다루는 과제가 시작되었다. 구현 전에 **관찰 → Why → 문제 정의** 순으로 정리하였다.

**핵심 결론**

- **표면 문제**: “4×4 마방진을 만드는 프로그램” — 목적·성공 기준이 불명확함.
- **개선된 문제**: 학습자가 제시한 격자 상태가 **정해진 마방진 규칙을 모두 만족하는지 일관되게 판정**하고, **명확한 피드백**을 제공하는 연습 환경을 정의·보장하는 것.
- **TDD를 택하는 이유**: 본질이 **다중 불변 조건을 동시에 만족하는가**라는 **계약 문제**이기 때문이며, 입력(격자 상태)·출력(판정)·불변(완성 조건)을 구현 전에 고정해야 함.

**Problem Framing 시 사용한 가정** (아래 [§3](#3-problem-framing-전제-가정) 참고)

- 학습·연습 맥락
- 사용자가 칸을 채우고 **규칙 충족 여부를 확인**하는 퍼즐형 경험
- 값 범위: 1~16 각각 한 번, 행·열·두 대각선 합 동일

## 2. STEP 1 — Observation (관찰)

### 2.1 Q: 현재 우리가 해결하려는 상황은 무엇인가?

**관찰된 상황**

- **4×4 격자**와 관련된 **규칙을 만족하는 배치**를 다루려는 의도가 표현됨.
- 그 의도는 아직 **구체적인 요구(입력·출력·제약·사용자)**로 고정되지 않음.
- **“문제를 먼저 정의하자”**는 절차적 선택이 먼저 나타남.
- 작업 공간(`MagicSquare_`)은 **프로그램 형태의 산출물**을 둘 **시작점**으로 보임 (당시 코드·문서 없음).

**아직 관찰되지 않은 것 (열린 질문)**

- “해결”이 **하나의 정답 탐색** / **모든 해 나열** / **사용자 직접 채우기** / **규칙 검증만** 중 무엇인지 미정.
- 4×4가 **고정 크기**인지 **학습용으로 4만 다루는 것**인지 미정.

**관찰 관점 한 줄 요약**

> 4×4 격자에 숫자(또는 값)를 배치할 때, 특정 합·대칭·중복 없음 같은 규칙과의 관계를 다루려는 **미정의 과제**가 시작되었다.

---

### 2.2 Q: 왜 4×4 마방진 문제를 다루는가?

**직접 관찰 가능한 이유**

- 사용자가 **4×4**와 **마방진**이라는 **명시적 범위**를 제시함 → “임의 크기 격자”가 아닌 **작고 완결된 인스턴스**로 범위 축소.

**가설 (확인 전)**

| 가설 | 근거 |
|------|------|
| 학습·연습 | 구현 전 “문제 인식” 단계 요청 |
| 복잡도 관리 | 3×3은 해가 적고, 5×5 이상은 방법·검증이 무거움 → 4×4는 손·코드 모두 다루기 쉬운 중간 크기 |
| 짝수 차 특성 | order 4는 홀수 차와 생성·증명·구현 논리가 달라 설계 학습에 자주 사용 |
| 검증·테스트 용이 | 행·열·대각선 합 등 불변량이 명확해 자동 검증·테스트 설계 연습에 적합 |

**관찰 관점 한 줄 요약**

> 범위가 작고 규칙이 명확한 격자 배치 문제를, 구현 전에 정의·관찰·학습 절차로 다루기 위해 4×4 인스턴스가 선택된 것으로 보임 (최종 동기는 사용자 확인 전까지 가설).

---

### 2.3 Q: 어떤 학습 또는 시스템 설계 맥락에서 등장하는가?

**학습 맥락**

- 수학·조합: 불변량(매직 상수), 순열·제약 만족, 대칭·회전 동치
- 알고리즘 입문: 백트래킹, 제약 propagation, 브루트포스 vs 구조적 생성(짝수 차)
- 소프트웨어 공학 입문: 요구사항 → 명세 → 검증 → UI/CLI 분리
- 테스트·품질: “올바른 배치”에 대한 **판정기(oracle)** 설계

**시스템 설계 맥락 (시스템은 아직 없음)**

- 도메인 **규칙 엔진**: “배치가 유효한가?” 중심
- **생성 vs 검증** 책임 분리
- **상태 공간 탐색**: 4×4 스케일에서 완전 탐색·휴리스틱 논의 가능
- 교육용·데모용: 격자 UI, 힌트, 단계별 피드백

**관찰 관점 한 줄 요약**

> 격자 배치 + 합·중복·대칭 규칙이라는 작은 도메인을, 알고리즘·검증·요구정의·UI 중 어디에 초점을 둘지 실험하기 좋은 **교육용 문제 인스턴스**로 자주 등장한다.

## 4. STEP 2 — Why #1

### Q: 왜 마방진을 완성해야 하는가?

**가정한 답 (A)**

> 16칸에 숫자를 올바르게 배치했을 때, 여러 줄의 합이 동시에 맞는다는 것을 직접 확인하고, 그 규칙을 몸으로 이해하기 위해 완성 과정을 거친다.

완성은 점수용 게임 목표보다 **“여러 제약이 한꺼번에 성립하는 배치”를 경험으로 확인하는 학습 목표**에 가깝다.

### 이 답에서 드러나는 불편함 · 구조적 문제

| 유형 | 내용 |
|------|------|
| 인지 부하 | 행·열·대각선·중복 없음을 동시 추적하기 어렵다. 한 줄만 맞춰도 다른 줄이 깨짐. |
| 피드백 지연 | 손계산·눈검사만으로는 “어디가 틀렸는지”가 즉시·정확히 드러나지 않음. |
| 오류 누적 | 초반 작은 실수가 나중 합 검증에서야 발견되면, 되돌리기 비용이 큼. |
| 완성 기준 모호 | “거의 맞음”과 “완전히 맞음” 경계가 사람마다 다름. 완성 정의가 공유되지 않으면 목표 달성 여부를 논하기 어려움. |
| 반복 학습 비용 | 같은 규칙 연습 시 검산·대조를 매번 처음부터 반복. |
| 구조적 난이도 (4×4) | 크기는 작지만 제약이 얽혀, 부분 해가 전체 해처럼 보이는 함정 발생. |

**구조적 문제 요약**

완성을 목표로 두면, 막히는 지점은 “16개 배치” 자체보다 **다중 제약의 동시 만족을 사람이 안정적으로 추적·판정·되돌리기 어렵다**는 점이다.

## 5. STEP 3 — Why #2

### Q: 왜 단순 계산이 아니라 프로그램으로 구현하는가?

### 5.1 반복 가능성

- 같은 4×4 상태에 **동일한 기준**으로 반복 판정 가능.
- 연습 세션을 나눠도 **판정 규칙이 흔들리지 않음**.
- “이번엔 대각선만 확인” 같은 **불완전한 반복** 감소.

### 5.2 검증 자동화

- 행·열·대각선·중복·범위 등 **여러 검사를 한 번에** 적용.
- 사람이 놓치기 쉬운 항목을 **누락 없이** 매번 검사.
- “완성 / 미완성 / 어떤 제약 위반”을 **일관된 결과**로 제공.

### 5.3 오류 방지

- 합계 실수, 중복, 범위 밖 값 등 **기계적 실수** 감소.
- 학습자는 산술·기록 오류 대신 **배치 전략과 규칙 이해**에 집중.
- 잘못된 상태를 “맞는 것처럼” 유지하는 **가짜 진행** 감소.

### 5.4 규칙 기반 사고 훈련

- “맞다/틀리다”를 감각이 아니라 **명시된 규칙 집합**에 대응.
- **입력(격자 상태) → 출력(판정·설명)** 분리 연습.
- 요구사항·테스트·모듈 경계로 옮기기 쉬운 **사고 단위** 형성.

**Why #2 한 줄 정리**

단순 계산은 한 번의 검산에 그치기 쉽고, 프로그램은 **규칙의 반복·자동·일관 적용**으로 학습·연습의 품질과 속도를 높이려는 선택이다.

## 6. STEP 4 — Why #3 (핵심 발견)

### Q: 왜 이 문제를 TDD 방식으로 설계하려 하는가?

### 6.1 무엇이 통제되어야 하는가?

| 통제 대상 | 이유 |
|-----------|------|
| “완성”의 의미 | 부분 만족 vs 완전 만족 구분 필요 |
| 판정 규칙 | 구현자·시간에 따라 달라지면 안 됨 |
| 입력의 유효 범위 | 빈 칸, 중복, 범위 밖 값 등 허용·거부 기준 고정 |
| 피드백의 의미 | “틀림”이 **어떤 제약 위반**인지 예측 가능해야 함 |
| 변경의 영향 | 규칙 수정 시 기존 예시 깨짐을 즉시 파악 |

TDD는 속도보다 **규칙이 의도대로 고정·회귀 없이 유지되는지**를 통제하려는 설계 태도다.

### 6.2 어떤 불변 조건이 존재하는가?

**도메인 불변 (완성 상태 기준)**

1. **범위·유일성**: 정해진 값 집합(1~16)에 속하며, 완성 시 각 값이 정확히 한 번.
2. **매직 합**: 모든 행·열·지정 대각선의 합이 **하나의 동일한 목표 합**.
3. **완성도와 판정의 일치**: “완성”이면 위 조건 모두 참, 하나라도 거짓이면 “완성” 아님.
4. **판정의 결정성**: 같은 격자 상태 → **항상 같은** 판정.
5. **부분 상태의 명확성**: 빈 칸·중복·범위 위반 시 “완성”이 아니거나 **별도 상태**(미완성·오류)로 분류.

### 6.3 왜 입력/출력이 명확해야 하는가?

| 이유 | 설명 |
|------|------|
| 테스트 가능성 | 격자 상태(입력)와 기대 판정(출력)을 사전에 적을 수 있어야 함 |
| 경계 분리 | 사용자 입력과 시스템 판정 책임 분리 |
| 회귀 방지 | 규칙 변경 시 깨진 예시를 입·출력 쌍으로 추적 |
| 학습 목표 정렬 | 출력만으로 다음 행동 결정 가능 |
| 모호성 제거 | “대충 맞음” 등 비형식적 판단 제거 |

### 6.4 Why #3 핵심 발견

TDD를 택하는 이유는 테스트 코드 양이 아니라, **마방진의 본질이 “다중 불변 조건을 동시에 만족하는가?”라는 계약 문제**이기 때문이다. 구현 전에 **입력·출력·불변**을 고정해야 학습·연습·자동 검증이 **같은 문제**를 가리킨다.

## 7. STEP 5 — 진짜 문제 정의

### 7.1 표면 문제 정의 (잘못된 정의)

> **4×4 마방진을 만드는 프로그램을 만든다.**

**문제점**

- “만든다”가 생성·퍼즐·데모·검증 중 무엇인지 불명확.
- 성공 기준(완성, 부분 점수, 힌트 등) 없음.
- 사용자 가치(학습, 놀이, 시연) 누락.
- 불변 조건과 판정 책임이 정의에 없음.

---

### 7.2 개선된 문제 정의 (정확한 정의)

> **학습자가 제시한 4×4 격자 상태가, 정해진 마방진 규칙(값의 범위·유일성, 행·열·대각선 합 일치)을 모두 만족하는지를 일관되게 판정하고, 그 결과를 명확한 피드백으로 제공하는 연습 환경을 정의·보장한다.**

**포함**

- 대상: 임의 시점의 격자 상태 (비어 있거나 채워진 상태 — 범위는 별도 명세)
- 핵심 행위: 규칙에 따른 **판정** (필요 시 위반 유형 구분)
- 품질: 같은 입력 → 같은 출력, 완성 정의와 불변 일치
- 목적: 검산 부담 감소, **규칙 이해·규칙 기반 사고** 훈련

**의도적으로 미포함**

- 화면 형태, 생성 방법, 힌트 전략, 해 탐색 등 구현·알고리즘 선택

---

### 7.3 핵심 Invariant

| ID | Invariant |
|----|-----------|
| I1 | 완성 인정 배치에서만, 허용 값 집합 원소가 **정확히 한 번씩** 사용됨 |
| I2 | 완성 인정 배치에서, 모든 관련 행·열·대각선 합이 **동일한 단일 값** |
| I3 | “완성” 판정은 I1·I2를 **모두** 만족할 때만 참 |
| I4 | 동일 격자 상태 → 판정 결과 **항상 동일** |
| I5 | I1 또는 I2 위반 상태는 **완성으로 분류되지 않음** |

### 7.4 실제로 훈련하려는 사고 능력

| 사고 능력 | 훈련 내용 |
|-----------|-----------|
| 다중 제약 동시 사고 | 하나의 배치가 여러 규칙에 동시에 묶임, 부분 만족 함정 인식 |
| 명세·계약 사고 | “맞다”를 검증 가능한 조건으로 표현 |
| 입·출력 분리 | 상태(입력)와 판정(출력) 책임 분리 |
| 불변 중심 설계 | 기능 나열이 아닌 **항상 지켜야 할 성질**부터 고정 |
| 회귀·변경 의식 | 규칙 변경 시 무엇이 깨져야 정상인지 예측 |
| 자동화 가치 판단 | 반복·오류·누락 작업을 규칙 엔진에 맡길지 판단 |

## 8. 단계 간 연결

```
STEP 1 관찰
  → 4×4 배치 + 규칙, 미정의 과제
       ↓
STEP 2 Why #1
  → 완성 = 규칙의 경험적 확인 / 다중 제약 추적의 어려움
       ↓
STEP 3 Why #2
  → 반복·자동 검증·오류 방지·규칙 기반 사고
       ↓
STEP 4 Why #3
  → 불변·I/O 계약 통제 (TDD = 계약 문제)
       ↓
STEP 5 진짜 문제
  → 일관된 판정 + 명확한 피드백의 연습 환경
```
